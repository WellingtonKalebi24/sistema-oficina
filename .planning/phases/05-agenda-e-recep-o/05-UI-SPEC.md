## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Required marker gap, icon gaps, compact appointment metadata |
| sm | 8px | Button rows, checklist item gaps, agenda chip internals |
| md | 16px | Default panel padding, grid gaps, form group rhythm |
| lg | 24px | Topbar horizontal padding, major form sections, agenda/filter separation |
| xl | 32px | Page horizontal gutter on desktop and major content separation |
| 2xl | 48px | Reserved for large workflow breaks; do not use inside dense reception panels |
| 3xl | 64px | Not used in Phase 5 operational screens |

Exceptions:
- Form controls keep the existing `min-height: 42px`.
- Mobile nav and primary touch rows keep the existing 44px-48px minimum target behavior.
- Compact agenda slots may use 12px internal padding to preserve scan density.
- Table action buttons keep the existing compact 32px-40px height depending on label length.
- File attachment rows may use 12px vertical padding when filename, type and size must remain readable.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label | 12px | 600 | 1.3 |
| Heading | 20px | 600 | 1.2 |
| Display | 28px | 600 | 1.15 |

Typography rules:
- Use only weights 400 and 600 in new Phase 5 UI. Existing heavier button styling may remain until normalized by a later visual cleanup.
- Page titles stay compact; do not introduce hero-scale or marketing type.
- Table headers use the Label role: uppercase, muted, 12px, weight 600.
- Agenda time labels, license plates, customer names and status badges must stay stable when values update.
- Letter spacing remains `0`; do not scale font size with viewport width.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#f4f7f6` | Page background and admin workspace field around panels |
| Secondary (30%) | `#ffffff` and `#eef3f1` | Panels, cards, forms, tables, sidebar/nav, muted agenda/filter strips |
| Accent (10%) | `#c58b2f` | Keyboard focus rings, active day/week selector, required-field companion emphasis, attention border for appointments due soon |
| Destructive | `#b4343a` | Cancel appointment, remove attachment, failed upload and destructive confirmations only |

Accent reserved for: focus outlines, active finite-mode selection when primary would imply completion, required-field companion emphasis, due-soon visual marker on agenda items and checklist attention states.

Semantic colors:
- Primary `#176b5b`: main submit actions, active navigation and completed check-in actions.
- Success `#237348`: saved, converted, uploaded and `Aguardando diagnostico` persisted states.
- Info `#2f66a0`: loading, neutral guidance, appointment source and read-only traceability metadata.
- Warning uses accent `#c58b2f` only for calculated or local visual attention; it must not create notifications, reminders, counters, inboxes or message-like UI.

## Phase 5 Interaction Contract

Navigation:
- Add `Agenda` as an operational nav item inside the existing authenticated admin shell when the session has the relevant agenda/reception read permission.
- Use a Font Awesome calendar-style icon for `Agenda`; use a clipboard/check-style icon for check-in actions when icons are needed.
- Keep the current two-column desktop pattern: left action/filter panel, right agenda/check-in list panel.
- On mobile, collapse to one column and keep all required agenda, check-in, checklist and attachment actions reachable.
- Do not add dashboard widgets, reminders, notifications or customer communication controls in this phase.

Screen structure:
- Use finite mode controls or tabs for `Agenda diaria`, `Agenda semanal`, `Check-ins` and `Anexos`.
- The agenda mode is the default first view.
- Daily agenda shows a chronological timeline or table grouped by hour.
- Weekly agenda shows one column per business day with compact appointment chips; horizontal scroll is allowed on narrow screens.
- Check-ins view lists received vehicles and allows consultation after reception.
- The check-in form must support two entry paths: from an appointment and direct from customer/vehicle data.

Agenda table and timeline:
- Appointment columns in table/list contexts: `Horario`, `Cliente`, `Veiculo`, `Placa`, `Servico previsto`, `Status`, `Origem`, `Acoes`.
- Appointment statuses must include at least `Agendado`, `Convertido` and `Cancelado`.
- `Convertido` means an appointment has a linked check-in; do not label it as merely concluded.
- Appointment-derived check-ins must visibly show the source appointment date/time in read-only metadata.
- Direct check-ins must create and display an automatically converted appointment for traceability.
- Agenda filters: date picker, day/week segmented mode, customer/plate search and status select.

Check-in flow:
- From appointment: `Fazer check-in` opens the check-in panel prefilled with customer, vehicle, plate and appointment metadata.
- Direct: `Registrar check-in direto` requires customer and vehicle selection/search before the checklist can be completed.
- On submit, successful check-in status is exactly `Aguardando diagnostico`.
- When check-in starts from an appointment, the appointment status becomes exactly `Convertido`.
- When check-in is direct, the UI must show the generated appointment row/chip as `Convertido` and linked to the check-in.
- The UI must never permit check-in without a tenant-scoped customer and vehicle selected; backend validation remains authoritative.

Checklist and reception data:
- Required check-in fields: customer, vehicle, received date/time and current mileage.
- Checklist fields: mileage, fuel level, damage notes, items left in vehicle and checklist items.
- Fuel level uses a finite select or segmented control with values `Reserva`, `1/4`, `1/2`, `3/4`, `Cheio`.
- Checklist items use checkboxes/toggles with visible labels and no icon-only controls.
- Damage notes use a textarea with concise helper copy: `Descreva avarias visiveis antes do diagnostico.`
- Items-left field uses a textarea or repeatable compact rows; each row must be readable in the check-in consultation view.
- Preserve Phase 3 permissive vehicle registration behavior; do not add new strict vehicle validation in this UI contract.

Attachments:
- Attachments belong to the check-in record and must display filename, type, size, upload state and actions.
- Accepted UI categories: `Foto`, `Documento`, `Outro`.
- Upload states: `Pendente`, `Enviado`, `Falhou`.
- Photo/file selection can be local preview/list before submit, but persisted state must come from the backend.
- Failed upload copy: `Nao foi possivel anexar o arquivo. Tente novamente ou remova o item da lista.`
- Removing an attachment is destructive and requires explicit confirmation naming the filename.
- Do not expose attachment URLs across tenants; UI must treat backend 403/404 as authoritative blocked or not-found states.

Tables and scan views:
- Persisted operational rows use tables or dense timelines, not marketing cards.
- Check-in list columns: `Entrada`, `Cliente`, `Veiculo`, `Placa`, `Status`, `Quilometragem`, `Combustivel`, `Anexos`, `Acoes`.
- Keep row heights stable when badges, attachment counts or statuses update.
- Use horizontal overflow for narrow screens rather than crushing columns.
- Empty states are text-only and operational; no illustrations.

Permissions and blocked states:
- Hide or disable actions when the session lacks the obvious permission, but always handle backend 403 with the existing blocked panel pattern.
- Suggested permission boundaries for planners: appointment read/write, check-in read/write, attachment read/write/delete.
- Unauthorized attachment access shows a server-permission blocked state, not a client-only explanation.
- Reception changes, appointment conversion and attachment mutations remain auditable by backend rules.

Confirmations:
- Cancel appointment requires explicit confirmation and uses destructive color.
- Remove attachment requires explicit confirmation naming the file.
- If editing a check-in after creation is allowed by backend scope, show a confirmation before changing mileage, fuel, damage notes or items left because those are audit-relevant reception facts.
- No confirmation should imply customer contact or message delivery.

Loading, empty and error:
- Loading preserves agenda/table/form dimensions with compact skeleton rows or inline status text.
- Empty agenda day/week state uses the copy in the Copywriting Contract.
- Check-in empty state: `Nenhum check-in encontrado para os filtros atuais.`
- Error states must not leak stack traces, connection strings, tokens, signed URLs, storage keys or Prisma details.
- Success and status messages use `role="status"` or equivalent when they update after an action.

Formatting:
- Dates and times use `formatDateTime` / `Intl.DateTimeFormat("pt-BR", { timeZone: "America/Sao_Paulo" })`.
- Date-only filters use `dd/mm/aaaa` presentation for Brazilian operators.
- Time slots use 24-hour format, for example `08:30`.
- Mileage uses integer kilometers with `km` label in display contexts.
- Currency is not a primary Phase 5 concern; if any service estimate appears, use existing `formatCurrency`.

Accessibility:
- Preserve 3px accent focus outlines.
- Buttons, filters, tabs, checklist toggles, upload controls and nav controls must be keyboard reachable.
- Icon-only controls are not allowed in Phase 5 unless they include accessible names and tooltips; prefer text labels for dense operational actions.
- Appointment and check-in status must not rely on color alone; include visible badge text.
- File input must have a visible label and expose selected filename(s) as text.
